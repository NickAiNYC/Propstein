# PropStein Live Sniper Delivery Report (A–G)

**Project**: PropStein Pro browser companion extension (visible-market intelligence layer)
**Branch**: `feat/live-sniper-foundation` (based on upstream `main` @ `c6789eb8`)
**Date**: 2026-10-30
**Iron rules**: Intelligence only — never place bets; no credential collection; no anti-bot circumvention; only markets visible on screen are analyzed; no fabricated numbers — every browser-observed price is labeled OBSERVED.

---

## A — Audit Conclusions

The full audit of `NickAiNYC/Propstein` (1,208 tracked files, 324 commits, Apache-2.0) established three baseline facts. First, PropStein is a real, running product: a FastAPI backend (`api/main.py`, 1,703 lines, deployed on Railway) plus a pure-frontend quant terminal (`viewer/`, deployed on Vercel, verifiably online at audit time), already featuring multi-source odds ingestion, a pre-kickoff-validated full-game reception model, a LangGraph five-gate alerting pipeline, SSE streaming, a CLV ledger with a receipt chain, Stripe and Whop monetization, and server-side entitlement verification. Second, **active on-screen market detection does not exist anywhere in the repository** — the pre-existing Chrome extension is merely a sidebar wrapper around the terminal, with no content scripts, no DOM reads, and no authentication, so the Live Sniper detection layer is entirely new construction. Third, and most critical as a negative conclusion: **the existing models are full-game scope**. The repository contains no possession-level probability model, no NFL real-time play-by-play data source, and no drive-level calibration corpus, so drive-scope markets must be delivered as "standalone baseline model + honest labeling," displaying NO MODEL COVERAGE until the evidence exists.

The audit also produced an explicit reuse/build/unsupported matrix and security findings S-1…S-8 (see `docs/LIVE_SNIPER_AUDIT.md`). This branch implements the extension-relevant mitigations one by one: S-1 (public markets endpoints) → all new `/api/v1/markets/*` routes require server-side auth; S-2 (client-forgeable tiers) → the panel renders only server-verified entitlements; S-3 (long-lived unscoped bearer token) → 15-minute scoped tokens; S-4 (stale host permissions) → a brand-new minimal permission manifest; S-6 (shared internal secret) → per-session tokens plus rate limiting.

## B — Architecture & Deliverables

The deliverable is a TypeScript monorepo (`extensions/`) plus an additive FastAPI router (`api/extension_router.py`; the only change to `api/main.py` is a two-line include, keeping the change reviewable and revertible). The four packages each have a single job. `@propstein/core` carries the market types, odds math, normalizer, matcher, DRIVE-REC-V1 model, freshness engine, signal state machine, and lifecycle registry — a pure-function library with zero platform dependencies. `@propstein/detection` carries the viewport visibility filter, an adaptive-batched MutationObserver differencer (16–200 ms adaptive batch window), and the adapter registry. `@propstein/browser` carries the origin-verified messaging protocol, untrusted-payload validation, and the per-origin site authorization model. `@propstein/ui` is the React terminal panel (signal cards, entitlement gate, state views, settings). The Chrome MV3 app (`apps/chrome`) contains the background service worker, an isolated-world read-only content bridge, and the side panel / companion pages; `demo/demo-sportsbook.html` provides a synthetic KC–NE live-market fixture (with scenario control buttons for price moves, suspension, drive switching, and reset, plus a 2-second heartbeat); `scripts/build.mjs` uses esbuild to produce the production, dev, and companion builds.

The data flow is one-directional: **visible DOM → read-only content bridge (events coalesced into batches) → adapters (versioned selectors, confidence scoring) → ObservedMarket canonical schema → normalization → matching → DRIVE-REC-V1 → signal state machine → panel**. The server contract (session issuance, revocation, health/kill switch, model coverage, evaluation) is aligned field-by-field with the extension's `model-provider.ts`.

## C — Pricing Math & Validation

The odds math is aligned clause-by-clause with spec §7 and locked in by 109 unit tests: American +160 → decimal 2.60 → breakeven 1/2.60 = 38.46%; EV (per unit stake) = p(d−1) − (1−p) = pd − 1; probability edge = p − 1/d; fair decimal = 1/p. Decisions use EV **after an uncertainty haircut** (shrinking the p-over-breakeven margin by 2%), with a +5% entry threshold, a +3% exit threshold (hysteresis), and a 30-second alert cooldown.

The drive-scope reception model DRIVE-REC-V1 uses the absorbing drive-termination closed form: P = q·(1−(s(1−q))^N)/(1−s(1−q)), where q is the per-play reception probability, N is the projected number of remaining plays in the drive, and s is the drive survival rate. The formula degenerates to the spec baseline 1−(1−q)^N at s = 1 and was verified by numerical alignment of the dual Python/TypeScript implementations (error < 1e-9). The synthetic demo parameters were numerically reverse-solved to hit the spec's worked example exactly: Kelce q = 0.1841, N = 8, s = 0.72 → P = 0.4399, which shows a 44.0% model probability and +14.4% EV (ALERTABLE) at +160; after clicking the price move to +115, the same signal instantly recomputes to a 46.51% breakeven and −5.4% EV (BELOW_THRESHOLD) — the complete numeric chain of Key Test 1. Calibration discipline enforces the 200-sample gate: below it, confidence labels read `insufficient_evidence` or `uncalibrated`; fabricated calibration confidence never appears.

## D — Detection System & Adapter Strategy

The detection layer's core promise is **analyzing only the markets the user can actually see**. A shared visibility predicate filters out every card that does not intersect the active viewport before parsing (virtual-list and off-screen cards never enter the pipeline); observation pauses the moment the watched tab loses focus; the bridge runs in the isolated world and contains no click/submit code paths. Change detection does not poll the whole page: MutationObserver records are aggregated over the adaptive batch window and set-differenced, producing seven event types — ADDED / ODDS_CHANGED / LABEL_CHANGED / STATUS_CHANGED / SUSPENDED / REMOVED / NAVIGATED. A defect found and fixed during integration is textbook-worthy: **when events were sent one-by-one, the REMOVED(old drive) + ADDED(new drive) pair produced by a drive switch raced against the background's drive-context adoption**, causing old-drive signals to be silently `remove()`d instead of being revoked via `driveEnded()`; the bridge now atomizes a switch into a single batch message through a 40 ms coalescing window, and the background adopts each batch's current drive context before processing revocations.

Adapters follow an authorization-gated model: demobook (the synthetic fixture) is the only enabled adapter; DraftKings / FanDuel / Polymarket exist only as feature-flag-disabled skeletons — enabling them is an operational act (written authorization + 30-snapshot selector validation + misparse canary tests + kill-switch version wiring + staged rollout), never a code default. Selector sets carry version numbers that propagate into revocation reasons, with the design goal that "a bad selector must fail loudly (card withdrawn) rather than fail silently (wrong price)." Polymarket prefers the already-authorized Gamma/CLOB API over the DOM.

## E — Security, Privacy & Compliance

The fulcrum of the security model is **fail-closed everywhere**; no fail-open path exists: membership unverifiable → session issuance returns 503, no model data; scoped token expired/tampered/revoked → markets routes return 401, the panel locks to SESSION_EXPIRED; server-side `EXTENSION_KILL_SWITCH=1` → health reports disabled, all protected routes return 503; a quote past the freshness cap (20 seconds live) → STALE revocation; market suspended → SUSPENDED revocation; drive ended → every signal from that drive is revoked; adapter confidence below 0.6 → UNVERIFIED, never alerted. Session tokens are HMAC-SHA256-signed (exp/iat/jti), with a 15-minute TTL, revocable by jti, requiring server-side Whop entitlement verification before issuance; issuance is rate-limited per principal (sliding window of 10/min, 429). Without `EXTENSION_SESSION_SECRET` configured in production, issuance returns 503 — never silent degradation.

On privacy: observed market DOM and signal snapshots **never leave the browser and are never written to disk**; the only credential is the user-pasted PropStein membership token (exchanged only over HTTPS with our own API for a scoped token, never placed in a URL query string); no telemetry, no crash reporting, no third-party scripts. The permission manifest is justified item-by-item against Chrome Web Store review standards (storage/scripting/tabs/sidePanel); host permissions are **zero at install time** and granted per-origin at runtime via user action. The content bridge treats all page data as untrusted input: length clamping, control-character stripping, a 200-event cap, and field-level sanitization. The compliance posture matches upstream: DK/FD player-prop data in this repository already flows through the authorized PropLine commercial API; the DOM adapters merely augment the display context of "the price the user is currently looking at" and sit behind the authorization gate.

## G — Deliverable Usage & Roadmap

**Run**: `cd extensions && npm install && npm run typecheck && npm run test:core`; `npm run build` produces `dist/propstein-chrome` (production manifest), `dist/propstein-chrome-dev` (localhost host permissions, for demo and e2e), and `dist/propstein-web-companion`. `npm run demo` serves the synthetic book on port 4173; `APP_ENV=development PROPWIRE_ALLOW_DEV_AUTH_BYPASS=1 uvicorn api.main:app` starts the dev backend; `chrome://extensions` → load unpacked → open the fixture page → side panel SIGN IN (the dev bypass accepts any non-empty token) → START MONITORING. Production deployment requires `WHOP_API_KEY`, `EXTENSION_SESSION_SECRET`, and adding the packaged `chrome-extension://<id>` origin to `ALLOWED_ORIGINS` (audit finding S-5, an operational action).

**Phase 2 (production wiring)**: the background's `RemoteApiModelProvider` and the new endpoint contract are already aligned field-by-field; the remaining work is wiring session tokens into `getSessionToken` and replacing the demo model with remote coverage — a day-scale wiring job that involves no new design. **Phase 3 (authorized live books)** is blocked on two external dependencies that only the owner can resolve: obtaining a possession-level NFL real-time data source (or written confirmation that DK/FD page observations may serve as model input) and written authorization for page-level DOM detection; until then, real books always show NO MODEL COVERAGE — which is precisely the intent of the honesty-first design. **Safari**: the conversion guide (`docs/LIVE_SNIPER_SAFARI.md`) lists the API compatibility checklist, the `storage.session` shim, and the side-panel alternative (the companion page reuses the same panel bundle); the core/detection/UI packages have zero platform dependencies, so conversion risk concentrates in the single background shim. **Quality roadmap**: once calibration data arrives, run DRIVE-REC-V1's Brier/log-loss/reliability curves (the module is built in; the 200-sample gate is enforced), and execute selector validation per the `docs/LIVE_SNIPER_ADAPTERS.md` checklist.
